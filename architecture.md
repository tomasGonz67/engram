# Architecture

## How Retrieval Works

Memory retrieval is a two-stage process:

**Stage 1 — Semantic Search (Qdrant)**
The query is embedded into a vector using the same model used to store memories — but not the same *framing*. Qwen3-Embedding is instruction-aware and its model card recommends prefixing queries (not documents) with a task instruction for retrieval; `search_memories()` prepends `RETRIEVAL_QUERY_INSTRUCTION` (`constants.py`) to the query text before embedding it, while stored memory text is embedded bare, matching the model's own config (an empty prompt for "document," a real one for "query"). See below for the empirical case this was tested against before adopting it. Qdrant finds the top N most semantically similar vectors using cosine similarity. Fast, pure vector math.

**Stage 2 — Re-ranking (Postgres)** — *implemented. See `dataModel.md`'s API section for the exact current response shape (kept as separate `semantic`/`retrievability`/`frequency`/`final_score` fields rather than collapsed to one `score`, for now).*
The N candidate IDs from Qdrant are used to fetch metadata from Postgres — `stability`, `use_count`, `last_reinforced_at`. A weighted formula re-ranks the candidates:

```
semantic = normalize_qdrant_similarity(raw_similarity)
frequency = 1 - exp(-use_count / 5)

final_score = 0.95×semantic + 0.05×frequency
```

`normalize_qdrant_similarity(raw_similarity)` is `(raw_similarity + 1) / 2` — cosine similarity is mathematically bounded to `[-1, 1]`, not `[0, 1]`, but `final_score`'s weighting assumes both terms share the same `[0, 1]` scale (which `frequency` already does, by construction). Without this rescale, a negative raw score would pull `final_score` down in a way `frequency` never does, breaking the intended proportions.

This is a weighted **sum**, not a product — deliberately, so that a weak signal on one term (e.g. a brand-new memory with `use_count = 0`) can't zero out the whole score the way a product would.

**What each signal is actually responsible for, and why `retrievability` isn't one of the ranking terms above**: semantic similarity provides the primary estimate of whether a memory is relevant to the current query at all — an estimate, not a determination; this document's own "How Retrieval Works" section above establishes that relevant and irrelevant scores measurably overlap for this embedding model and dataset, so no score alone proves relevance. It dominates the formula (95%) so an irrelevant memory can't win purely by being old or heavily used. `frequency` provides a small, deliberate bias toward memories estimated to have been genuinely useful before (5%) — a nod to real use mattering, without letting it override topical relevance. `retrievability` — how "accessible" a memory is based on decay since last use — governs Decay-Based Forgetting's deletion threshold (see below) but does **not** influence retrieval ranking, as of an evidence-backed decision, not an oversight: an empirical evaluation found that giving `retrievability` any ranking weight at all, even as little as `0.01`, caused real relevance regressions on this dataset's current reinforcement state, with no measured benefit at any weight tested. See `evaluation/experiments/reranking-weight-decision.md` for the full hypothesis, predeclared decision rule, results, and honest limitations (small hand-built fixture, one live database snapshot — not a claim these weights are universally optimal or neuroscientifically derived), and `security-preventions.md`'s Resolved section for the summary. This is inspired by how human memory accessibility fades with disuse, not a mechanistic model of the brain — decay still shapes what eventually gets forgotten, it just no longer shapes what ranks highest for a given query.

**No hard semantic-score cutoff** — there used to be one (`SEMANTIC_THRESHOLD`, discarding any candidate below a fixed value before ranking), removed after being measured as unreliable rather than just untuned. History: `0.7 → 0.8 → 0.75`, each move chasing a real failure the previous value caused — a nonsense query leaking noise past `0.7`, then a genuinely relevant query ("do I have a girlfriend?") getting wrongly filtered out entirely at `0.8`. The value that killed the approach outright: against a 181-memory dataset, the single *best* real match for that girlfriend query — ranked #1 out of 181 — still scored only `0.71`, below `0.75`, while real (non-nonsense) content scored as high as `0.79` against a totally unrelated nonsense query. Relevant and irrelevant scores genuinely overlap for this embedding model and dataset, so no single cutoff can separate them without either blocking real matches or letting noise through — moving the number just changes which failure you get, not whether one happens. See `security-preventions.md`'s Resolved section for the full history. Relevance is now judged downstream instead of at the retrieval boundary — see the "second defense layer" note below, and the reinforcement guardrail in "How Generation Works," which is unaffected by any of this (it answers a different question — see `constants.py`).

**Why this overlap happens at all**: it's not specific to this dataset or a sign of a bad embedding model — it's a known property of short-text embedding similarity in general. Two things compound here. First, embedding spaces from transformer models aren't spread evenly across the vector space; most vectors cluster within a narrow region (a property called anisotropy), so even genuinely unrelated pairs of text end up with a surprisingly high baseline cosine similarity — the useful range between "clearly related" and "clearly not" is smaller than it intuitively seems. Second, short text just doesn't carry much disambiguating signal — a phrase like "Met my girlfriend Madeline playing Toontown" or a short query doesn't give the model much to anchor on to distinguish "this is precisely it" from "this is vaguely in the same territory." Longer text gives embeddings more to work with; the memories in this dataset, and most natural queries against them, are both short. This exact same limitation is why the reinforcement guardrail's threshold (see "How Generation Works" below) also can't be perfectly calibrated — a genuine citation buried in a short sentence fragment and a generic filler phrase run into the identical noise floor. Two different symptoms, one shared root cause.

Both of these effects are real, but they weren't the whole story — retrieval queries were also missing Qwen's recommended instruction prefix (see above), and that turned out to be a genuine, measurable contributing factor. Tested directly, not assumed: 23 labeled positive queries plus 4 negative controls against the complete 181-memory development snapshot that existed at the time, comparing bare queries against the instruction-prefixed form. Negative-query separation improved consistently — mean highest similarity for an irrelevant query dropped from `0.762` to `0.683`, maximum from `0.825` to `0.748` — and final-ranking Recall@5 (how many of the genuinely relevant memories for a query survive into the top 5 after re-ranking, not just raw semantic similarity) rose from `67.0%` to `78.9%`. But the overlap didn't close: even with the instruction, the lowest genuine-match score measured (`0.702`) still sits below the highest irrelevant-query score measured (`0.748`). So the instruction prefix is a real, adopted improvement (see `constants.py`'s `RETRIEVAL_QUERY_INSTRUCTION`) — it narrows the overlap — but it doesn't eliminate it, and doesn't change the "no hard threshold" conclusion above. The anisotropy/short-text explanation and the missing-instruction gap were both true at once; fixing one didn't turn out to fully explain away the other.

N is intentionally larger than the number of results returned. Fetch top 50 from Qdrant, re-rank all of them, return top 5 by `final_score` — no filtering step in between. This gives the re-ranking enough candidates to work with, and means retrieval basically always returns exactly `limit` results (whatever's closest, even if weak) rather than sometimes returning fewer or none.

`search()` still returns `{"message": "No valid memories found"}` instead of an empty array if nothing comes back — a deliberate exception to keeping the response type uniform, chosen over faking a memory-shaped placeholder object (a fake `id`, an out-of-bounds `final_score` like `100`) just to preserve a single type. This is now a rare case (an empty Qdrant collection, or candidates with no matching Postgres row) rather than the common "nothing cleared the threshold" outcome it used to be. See `dataModel.md`'s API section for the exact shape.

**Evaluation scope:** every numerical result in the preceding threshold and query-instruction discussion was measured against the former 181-memory development snapshot. The current canonical seed corpus contains 1,000 different memories, and the old fixture is stale against it. These results remain the historical basis for the prototype defaults, not validation of retrieval quality on the current corpus; see `evaluation/README.md`.

## How Generation Works

`/generate` is the "AG" half of RAG, built on top of retrieval:

1. **Retrieve** — `search_memories()` (shared with `/memories/search`, see Controller section below) runs the query through the same embed → search → rank pipeline as Stage 1/2 above, returning the top `limit` ranked memories. `/generate` doesn't embed the new message alone — it prepends the last `RETRIEVAL_CONTEXT_TURNS` (`constants.py`, currently 2) turns of conversation first, so a context-dependent follow-up ("tell me more details", "why?") carries some retrievable meaning instead of being embedded with zero context about what it's following up on. Deliberately small — unlike the generation prompt (which benefits from more history), folding in many turns here risks diluting the retrieval embedding the same way a long `/generate` answer was found to dilute the reinforcement guardrail's embedding (see step 5 below). `/memories/search` has no conversation to draw on and is unaffected — this only applies to `/generate`.
2. **Assemble the prompt** — system prompt + retrieved memories (as `(id) [time ago] text` lines, e.g. `(abc123) [3 years ago] Met my girlfriend playing Toontown` — the `[time ago]` marker is computed fresh from `created_at` via `formulas.humanize_age()` on every request, so it's always accurate regardless of how much real time has passed since storage, rather than a relative-time phrase frozen into the stored text itself) + the caller-supplied `recent_turns` + the new query, all as one `messages` list sent to the generation model (`gpt-5.4-nano`, see `techStack.md`).
3. **One completion call, no tools** — the model just writes its answer. No function calling is involved at all. This is a deliberate architectural decision, not the original design — see below for what was tried first and why it was dropped.
4. **Guardrail decides reinforcement, independently of the model** — every memory in `retrieved` (not just ones the model happened to mention) gets checked against the answer that was actually written, entirely in code, no second model call involved. The answer is split into sentences (`formulas.split_into_sentences()` — blank lines/bullets first, then sentence-ending punctuation within each), and each retrieved memory is compared against every sentence individually via the same `SentenceTransformer` model used for storage/retrieval, taking the *best*-matching sentence's score rather than embedding the whole answer as one block — this matters for long, multi-topic answers, where generic wrapper text (greetings, transition phrases, a closing "want to hear more?" question) was measured to dilute a whole-answer embedding enough to drag a genuinely-cited memory's similarity below threshold, even when one specific sentence in it was a near-exact paraphrase. A memory only gets reinforced if its best sentence-match clears **both** `REINFORCEMENT_GUARDRAIL_THRESHOLD` (`constants.py`, currently **0.8**) **and** `formulas.shares_significant_word()` — at least one non-stopword literal word in common with that sentence. The second condition exists because pure embedding similarity was found, live, to false-positive on shared narrative *shape* regardless of actual content (e.g. "tried kombucha, hated it" scoring above threshold against an answer about giving up on sushi, zero shared content) — see `security-preventions.md`'s Resolved section. Memories clearing both get passed to the real `reinforce_memory()` function in `memory_operations.py`, which updates `stability`/`use_count` in Postgres and returns the normalized id (used in the response's `reinforced_memory_ids`).

**Why there's no function calling**: the original design exposed `reinforce_memory` as a tool the model could call, eventually with `tool_choice="required"` forcing at least one call per request. This was tried, tightened twice, and ultimately dropped — not because tool calling itself is unreliable in general, but because once the guardrail exists as the actual decision-maker, the model's tool call stopped adding anything the guardrail wasn't already independently checking via embedding similarity, while still adding real problems of its own: the model repeatedly skipped calling the tool even when it clearly cited a memory (a real citation going uncredited), and separately, when an answer cited *multiple* memories, the model would sometimes call the tool for only some of them rather than all — forcing at least one call (`tool_choice="required"`) fixed the first problem but not the second. Once every retrieved memory is checked against the answer directly, regardless of what the model flagged, both problems disappear at once: nothing depends on the model remembering to flag anything. This also halved the cost — one completion call instead of two. See `security-preventions.md`'s Resolved section for the full history, including the intermediate steps (an answer-first/reinforce-second ordering, then `tool_choice="required"`) that got tried and superseded along the way.

The guardrail's own embedding comparisons are local (no OpenAI call) and don't affect this cost either way.

**Why this was foreseeable, in hindsight**: writing the answer and deciding "did I actually use memory X" look like the same kind of task, but they're not. Writing the answer is generation — open-ended, genuinely requires judgment, exactly what an LLM is built for. Deciding whether a specific memory shows up in text that already exists is verification — an objective, checkable fact about that text, not a judgment call. LLMs aren't structurally reliable at the second kind of task, because generating the answer and generating the tool call are two separate predictions, not one unified act of self-reflection — the model isn't literally re-reading its own output with certainty when it decides whether to call the tool, it's producing another plausible-sounding guess, and nothing guarantees that guess matches what it actually wrote. That's the same shape as every failure this section describes: forgetting a citation, flagging only some of several, or (in the earliest version) predicting a citation before the answer even existed. Comparing two pieces of text for similarity, by contrast, is deterministic — the same two inputs always produce the same output, no risk of the check itself "forgetting" something between one run and the next. Deterministic is not the same claim as accurate, though, and this guardrail is only the former: embedding similarity is an estimate of whether a memory is reflected in the answer, not a ground-truth determination, and it has a measured false-positive rate for short text (see `techDebt.md`). The lesson generalizes beyond this one feature: don't ask a generator to also be its own reliable auditor — if a decision can be reduced to a deterministic comparison, a separate deterministic mechanism will be more trustworthy than asking the model to self-report, even though asking the model feels like the more natural place to put that logic. "More trustworthy than the model's self-report" is a comparative claim, not a claim that the comparison itself is error-free.

**`REINFORCEMENT_GUARDRAIL_THRESHOLD` itself**: not the old retrieval threshold reused — that one answered "does this memory match the query," this one answers "does this memory match the answer." Empirically tested against ~15 generic/filler answers and ~11 answers that genuinely cited a memory, across several different memory texts — filler topped out at `0.837`, genuine citations started at `0.879` at the whole-sentence level, a clean gap that `0.85` originally sat inside. But a genuine citation buried inside a parenthetical clause within a longer sentence was later found to score only `0.81`-`0.83` even at finer chunk granularity — below `0.85`, and *below* the `0.837` filler ceiling too. Genuine and filler measurably overlap at this fine a grain, so no single value cleanly separates them; `0.8` is a deliberate, known-imperfect tradeoff (catches more real citations, accepts letting some filler back through) rather than a cleaner calibration — see `security-preventions.md`'s Resolved section for the full reasoning. A hybrid embedding + literal-word-overlap check was proposed here as an *OR* (pass on either signal, to catch more genuine citations) and not built at the time; a version of it **has since been built**, but as an *AND* (`formulas.shares_significant_word()`, see step 4 above) — aimed at a different, later-discovered failure mode (confidently-wrong reinforcement on shared narrative shape, not under-scored genuine citations). Unaffected by retrieval no longer having a threshold at all (see "How Retrieval Works" above) — it answers a different question entirely. Same root cause as retrieval's threshold problem, though: a short sentence fragment compared against a short memory text runs into the exact same short-text embedding noise floor described in "How Retrieval Works" above — not a coincidence that both thresholds turned out to be unreliable in the same way.

The response returns the answer, which memory IDs actually got reinforced (a subset of `retrieved` — every candidate is checked, only some pass), and the full `retrieved` list, so a caller can see what was available even if the answer didn't use all of it.

**A second defense layer against retrieval noise, since there's no filter at retrieval anymore**: without a threshold, `/generate` always hands the model `limit` memories, even for a genuinely nonsense query — confirmed live: a gibberish query still returned 5 candidates (all scoring 0.81+ against unrelated real content), yet the model's answer correctly recognized the input as gibberish and didn't fabricate anything from that irrelevant context. This relies on the system prompt's "ignore what's not relevant" instruction for the *answer text* — retrieval and generation aren't a single point of failure, a bad retrieval result doesn't automatically become a bad answer, as long as the model actually follows that instruction (not guaranteed, but there's no deterministic backstop for the answer text itself either way). Reinforcement doesn't depend on this at all, though — the guardrail checks every retrieved memory against the answer regardless of the model's judgment, so a nonsense query's irrelevant candidates get correctly rejected on textual grounds even if the model's own restraint somehow failed. Confirmed live: a gibberish query with junk data in the retrieved pool reinforced nothing.

## Memory Lifecycle (Decay, Reinforcement, Decay-Based Forgetting)

**Constants**
```
BASE_STABILITY = 1.0
REINFORCEMENT_MULTIPLIER = 1.2
MAX_STABILITY = 3650.0        (days, ~10 years — a safety rail, not meant to be reached)
MIN_IMPACT = 0.5
MAX_IMPACT = 2.0
```

**On creation**
```
impact = clamp(provided_impact ?? 1.0, MIN_IMPACT, MAX_IMPACT)
stability = BASE_STABILITY × impact
use_count = 0
retrieval_count = 0
last_reinforced_at = now()
```
`impact` seeds `stability` here at creation, and only here — it deliberately plays no role in Decay-Based Forgetting's deletion threshold (see below). An earlier design used `impact` twice (seeding `stability` *and* dividing the deletion threshold), giving high-impact memories a compounding advantage; that was rejected as double-counting a single signal, so `impact`'s influence flows through `stability` — including later reinforcement — while the deletion threshold stays flat and impact-independent. There is no separate "importance"/"attention"/"emotional_salience" field; those all collapse into `impact`, which is the one explicit signal available at write time (unlike e.g. difficulty, which would need real outcome/feedback data this system doesn't have).

**Retrievability — computed lazily, never stored**
```
retrievability = (1 + age_days / stability)^(-0.5)
```
Important: `stability` is **not** a half-life. At `age_days = stability`, retrievability is ~70.7%, not 50%. The actual half-life is `3 × stability`. Computing this on the fly (rather than a stored, periodically-updated `strength` column) means it's always exact and needs no background decay job.

This specific power-law-shaped decline (`(1 + age_days/stability)^-0.5`, rather than e.g. a simple exponential) is loosely inspired by research finding that human forgetting is often better described by a power function than other candidate curve shapes (Wixted & Ebbesen — see References below) — "often," not universally: the broader retention-function literature finds several plausible mathematical families, not one settled, single "the" forgetting curve. Treat this formula as a defensible, loosely-motivated engineering choice, not a claim that human memory provably follows this exact equation.

`compute_retrievability` raises `ValueError` if `stability <= 0` rather than letting the calculation proceed — Python's `**` on a negative base with a fractional exponent silently returns a complex number instead of erroring, which would otherwise corrupt `final_score` without any visible failure at the point something actually went wrong. `compute_initial_stability` also clamps its own input internally now, so it can't produce an invalid `stability` regardless of whether the caller already validated `impact`.

**On search — a memory is returned as a result**
```
retrieval_count += 1
```
Does **not** touch `stability`. Being shown is not reinforcement — see below for why.

**On meaningful use — explicit signal only, not automatic**
```
stability = min(stability × REINFORCEMENT_MULTIPLIER, MAX_STABILITY)
use_count += 1
last_reinforced_at = now()
```
Reinforcing on every search *return* (rather than meaningful use) creates a self-reinforcing popularity loop: a memory ranks well → gets shown more → gets reinforced just from exposure → ranks even better. Splitting `retrieval_count` (shown) from `use_count` (meaningfully used, estimated via the reinforcement guardrail — see "How Generation Works" for what that estimate can and can't establish) avoids that — only estimated meaningful use should make a memory more durable.

Loosely inspired by the **testing effect** — active retrieval of information improves later retention more than passive re-exposure does (Roediger & Karpicke — see References below). The mapping here is an engineering analogy, not an implementation of that research: the testing effect concerns a human actively retrieving information from their own memory, and an LLM having a memory's text placed directly into its prompt and paraphrasing it is not the same process. Retrieval-practice benefits are real; this project does not implement the cognitive task those studies actually measured.

The `MAX_STABILITY` cap exists because reinforcement is multiplicative and otherwise unbounded — without it, a heavily-used memory's `age_days / stability` ratio would trend to ~0 for any realistic elapsed time, making retrievability permanently ~100% even after years of neglect. That defeats the entire point of decay for exactly the memories that were reinforced the most.

**Deferred, not built**: a Difficulty parameter, a Confidence parameter, and a variable reinforcement gain (bigger stability boost for memories that had decayed further before being reinforced) are all documented as considered-and-deferred in `techDebt.md` — none has a real signal driving it yet, or isn't needed for a working v1.

**Decay-Based Forgetting — implemented.** The prototype approximates forgetting by permanently deleting memories whose modeled retrievability falls below a threshold, deleting them from both Postgres and Qdrant as part of the same operation — same reasoning as `scripts/clear.sh`. Not atomic, though: `delete_memories()` is two sequential operations (Postgres then Qdrant), same non-atomicity as `store_memory()`'s writes — a failure between the two can still leave an orphan in whichever store didn't get the second call. See `techDebt.md`'s "Non-atomic dual-store writes/deletes" entry for the honest accounting of this.

```
delete if retrievability < MIN_RETRIEVABILITY
```

A flat threshold, deliberately not scaled by `impact`. An earlier design used `threshold = MIN_RETRIEVABILITY / impact`, loosely inspired by **flashbulb memory** research. Research reviewed by McGaugh (2004) indicates that emotional arousal can modulate long-term memory consolidation through stress-hormone and noradrenergic activity involving the basolateral amygdala — a narrower, sourced claim than "enhancement of hippocampal LTP," which an earlier version of this document asserted without a source that directly establishes that specific mechanism. `impact` is only a loose engineering analogy to that broad effect, not a biological implementation — this project makes no claim about accuracy, and doesn't model it.

Durability is not the same as accuracy, and that distinction matters as a counterweight: Neisser & Harsch's Challenger-disaster study — often reached for as if it supported a durability mechanism, which is a misreading worth naming explicitly since an earlier version of this document made exactly that mistake — actually found the opposite kind of thing: people's vivid, high-confidence "flashbulb" memories of hearing the news changed substantially over the following years despite their confidence staying high. That's a caution about vividness/confidence not guaranteeing accuracy, not evidence for an encoding-boost mechanism.

That McGaugh-reviewed research still motivates `impact` seeding a higher initial `stability` — but using it a second time, to also relax the deletion bar, was judged to double-count the same signal and give high-impact memories a disproportionately compounding advantage. `stability` (seeded by `impact`, grown by real reinforcement) is now the sole carrier of "how durable is this memory" — the deletion threshold stays universal and easier to reason about.

`MIN_RETRIEVABILITY = 0.01` was chosen by calculating expected deletion ages across representative stability/impact/reinforcement combinations, then checking those numbers against this project's own live seeded dataset (181 memories, ages spanning decades per `scripts/backdate.sh`) rather than trusting the formula in isolation. A more conservative candidate, 0.02, was tried first and rejected: it still made 54% of that live dataset — mostly genuine, never-reinforced autobiographical memories, not noise — immediately eligible for deletion, which read as too aggressive for a system meant to model long-term autobiographical retention. At `0.01`, a never-reinforced memory becomes eligible for deletion after ~13.7 years at min impact (0.5), ~27.4 years at baseline impact (1.0), ~54.8 years at max impact (2.0); anything genuinely reinforced (`stability` near the `MAX_STABILITY` cap) is effectively never deleted. Reproducible via `scripts/forgetting_threshold_analysis.py`. This is an MVP default, not a biologically validated value — no claim these specific durations match real human forgetting curves, only that they're no longer obviously mismatched for this dataset.

Because this permanently deletes data, `delete_decayed_memories()` takes a `dry_run` flag: when true, it computes and logs exactly which memories would be deleted without deleting them. `main.py` wires this to `FORGETTING_DRY_RUN` (env var, defaults to `true`) — the loop runs in report-only mode by default, so a real deployment must explicitly opt into deletion after inspecting at least one dry-run cycle's output against real data, rather than the newly-changed threshold silently starting to delete things on day one.

Each memory's retrievability computation is wrapped in its own `try/except ValueError` — a single malformed row (`stability <= 0`; nothing in the schema prevents this, only app-level clamping at write time) is logged and skipped rather than raising uncaught and killing the entire weekly loop for every other memory. See `techDebt.md`'s Resolved section for the failure mode this replaced.

**Threshold-validation scope:** the 181-memory live-data check above predates the current 1,000-memory seed corpus and has not been repeated against it. The calculated lifetimes still follow from the implemented formula, but the percentage of the current dataset that would qualify for deletion is not established. Dry-run remains the required safety step before enabling deletion.

**Runs on a weekly `asyncio` loop inside the app, not a manual script or an HTTP route.** Three deliberate choices here:

1. **Automated, not manual** — unlike `scripts/seed.py`/`scripts/clear.sh` (both hand-triggered), the forgetting loop runs on its own for as long as the app is up. The backend is already a long-running process, so a loop started in `main.py`'s `lifespan` (`asyncio.create_task`, cancelled on shutdown) costs nothing extra to add — no new dependency (no APScheduler), no OS-level cron needed.
2. **Weekly, not daily** — chosen for the actual timescale of decay, not performance. Each run is cheap regardless of interval (a small table scan, pure-Python math, a batched delete — no external API calls, unlike `/generate`), so interval doesn't meaningfully affect cost. Retrievability now moves on a scale of years-to-decades (see the numbers above), so weekly is a conservative check rather than a tightly-matched one — daily would just re-scan a table that's barely changed since yesterday, and even monthly would still be defensible; weekly was kept as a reasonable, cheap default rather than re-tuned for the new timescale.
3. **No HTTP route** — this is destructive (real deletions), and Masi Memory has no auth by design (see the project decision to never add it). A public `POST /forget` would let anyone on the internet trigger mass deletion. Keeping it as an internal-only background loop means there's no route to protect in the first place.

**Why a real thread (`asyncio.to_thread`), not just `async`/`await`.** These solve different problems and get confused easily. Plain `async`/`await` is cooperative concurrency on a *single* thread — coroutines only yield control at `await` points, so a blocking call with no `await` in it (like a synchronous `psycopg2` query) hogs that one thread completely, stalling every other request (`/generate`, `/memories/search`, everything) until it finishes. Wrapping the blocking DB work in `asyncio.to_thread()` instead hands it to a real, separate OS thread from a shared pool — the event loop stays free to keep serving requests while that thread does its own work in parallel, and `await` just means "resume this coroutine once that thread's result is ready." This is the same mechanism FastAPI already uses under the hood for every plain-`def` route (`run_in_threadpool`) — the forgetting loop just applies the identical pattern explicitly, rather than introducing a new one. One caveat worth naming: Python's GIL means threads don't buy true CPU-parallelism — two threads can't execute Python bytecode at the same instant — but the GIL releases during I/O waits (a network round-trip to Postgres or Qdrant), which is exactly what this workload is, so the threading genuinely helps here despite the GIL.

## Code Architecture (MVC)

Layered architecture mapped to MVC:

- **Model** — split across two files:
  - `models.py` — data shapes. Defines what request/response data looks like using Pydantic. No logic, no DB, just structure.
  - `database.py` — data access. Holds the Qdrant client, embedding model, and the Postgres connection helper. Plain functions that take already-finished values and read/write them — no business logic, no clamping, no derived-value computation. Reads all connection info from environment variables — no hardcoded credentials.
- **View** — `frontend/` (React + Vite). Talks to `/generate` directly, no server-side logic of its own — see `techStack.md`.
- **Controller** — split across two places, same role (orchestration: fetch, compute, write), split by whether it's wired to an HTTP route:
  - `routers/` — actual HTTP routes. Each file is a resource (memories, generate). Owns business logic, calls `formulas.py` for calculations and `database.py` purely for reads/writes, returns responses. Two plain functions in `routers/memories.py` exist independently of their own route so other internal callers can use them directly: `search_memories()`, shared by `/memories/search` (returns ranked results directly, no LLM involved — used for debugging/calibrating ranking, e.g. surfacing exactly how weak a match is instead of it being silently filtered out) and `/generate` (feeds the results into the generation prompt); and `store_memory()`, extracted from `/memories`'s route so it has a shape other internal callers could use directly. `created_at`/`last_reinforced_at` are dev-only backdating hooks the public route never passes, not exposed through `MemoryInput` at all — see `dataModel.md` and `security-preventions.md`. `scripts/seed.py` still creates memories via the real HTTP API — the backdating need ended up solved a different way (`scripts/backdate.sh`, a SQL-only post-process step; see `techDebt.md`'s Resolved section and `scripts.md`), so `store_memory()`'s timestamp parameters remain a real, tested capability with no current caller, available for any future in-process use. Both functions exist so their respective logic can't drift between callers — same reasoning as `formulas.py`.
  - `memory_operations.py` — orchestration with no dedicated HTTP route of its own (e.g. `reinforce_memory`). Now has a real caller: `/generate`'s reinforcement guardrail invokes it directly for each retrieved memory whose text passes both the embedding-similarity and literal-word-overlap checks against the model's answer — no function calling involved; see "How Generation Works" above for what that estimate can and cannot establish. Same internal shape as a router function, just not wrapped in its own route — could still get one later (e.g. `POST /memories/{id}/use`) if a caller other than `/generate` needs it.
- **App entry point** — `main.py` — app setup, lifespan, router registration. No business logic.
- **Formulas** — `formulas.py` — every calculation from this doc (impact clamping, stability, retrievability, frequency, semantic normalization, final score) as pure, independently testable functions. Not part of the MVC split itself — routers call into it rather than computing things inline, so the same math can't drift between call sites (e.g. Decay-Based Forgetting reuses `compute_retrievability` too, via `memory_operations.py`).
- **Constants** — `constants.py` — shared, tunable values (see below). Imported by `formulas.py` (most of them) and directly by `routers/` for the few that are orchestration parameters rather than formula inputs (e.g. `CANDIDATE_POOL_SIZE`). Not part of the MVC split itself, just a single source of truth so tuning values live in one place instead of scattered across the codebase.

Concerns are separated by responsibility. Structure expands as complexity justifies it — not prematurely.

## References

Every scientific claim this document makes by author/year, in one place with verifiable sources — added specifically because one of these (McGaugh, below) was previously cited in support of a claim it didn't actually establish, caught and corrected during review. Formal citations exist so that mistake is checkable and correctable, not just trusted.

- McGaugh, J.L. (2004). The Amygdala Modulates the Consolidation of Memories of Emotionally Arousing Experiences. *Annual Review of Neuroscience*, 27, 1-28. https://doi.org/10.1146/annurev.neuro.27.070203.144157 — cited in the Decay-Based Forgetting section for the narrow claim that emotional arousal can modulate memory consolidation via amygdala/noradrenergic activity. Motivates `impact` seeding initial `stability` only; does not establish "enhancement of hippocampal LTP" specifically, and this document no longer claims that.
- Neisser, U. & Harsch, N. (1992). Phantom flashbulbs: False recollections of hearing the news about Challenger. In E. Winograd & U. Neisser (Eds.), *Affect and Accuracy in Recall: Studies of "Flashbulb Memories"* (pp. 9-31). Cambridge University Press. https://www.semanticscholar.org/paper/889678f5d6c9be0550253d964756eadbc8d482d7 — cited in the Decay-Based Forgetting section as the counterweight to the McGaugh citation above: vivid, high-confidence "flashbulb" memories can still be substantially inaccurate. Evidence against treating confidence/vividness as a proxy for accuracy, not evidence for (or against) a durability-enhancing encoding mechanism.
- Roediger, H.L. & Karpicke, J.D. (2006). Test-Enhanced Learning: Taking Memory Tests Improves Long-Term Retention. *Psychological Science*, 17(3), 249-255. https://doi.org/10.1111/j.1467-9280.2006.01693.x — cited in "On meaningful use" as the loose inspiration for reinforcing memories on estimated use rather than mere exposure. The testing effect concerns a human actively retrieving information from their own memory; this project's guardrail instead checks whether an LLM answer appears to reflect text supplied in its prompt, using embedding similarity plus literal word overlap. That is an engineering analogy, not an implementation of the retrieval-practice task studied in humans.
- Wixted, J.T. & Ebbesen, E.B. (1991). On the Form of Forgetting. *Psychological Science*, 2(6), 409-415. — cited in the Retrievability section as loose motivation for a power-law-shaped decay formula rather than an alternative curve shape (e.g. simple exponential). "Often well described by," not "universally follows" — the broader retention-function literature has multiple plausible candidate curve families, not one settled function.
