# Tech Debt

## Open

- **Evaluation fixture (`evaluation/retrieval_cases.json`) is invalid against the current 1,000-memory seed dataset — highest-priority item on this list.** Confirmed directly: all 86 unique `relevant_memory_texts` across its 23 positive cases were written against the former ~181-memory corpus and none exist in the current `scripts/seed_data.json`. `validate_fixture()` will fail fatally, before running any evaluation, against a freshly reseeded dev DB. This means every retrieval number currently published in `evaluation/README.md` and `evaluation/experiments/reranking-weight-decision.md` — including the evidence behind the `0.95/0.00/0.05` ranking-weight decision in `constants.py` — describes the old corpus, not the current one, and hasn't been re-measured since the rewrite (see the staleness notes added to both of those files). Needs: a new fixture built against the current 1,000-memory dataset (ideally exercising the paraphrase/contradiction/needle/adversarial buckets specifically, not just the background/cluster ones the old fixture resembled), then a full rerun of every reported experiment before treating any current retrieval-quality claim as verified. Not done here — flagged by external review, confirmed independently, deliberately left as tech debt rather than fixed in the same pass as the corpus rewrite that broke it.

- **No automated testing** — no unit or integration tests. Acceptable for a personal project at this stage. One deliberate, scoped exception: `backend/test_trusted_proxy.py` — see the "Reverse proxy trust" entry below for why this specific piece got a real test file instead of the usual manual-verification pattern. An external review flagged this as a growing risk rather than a static one: core behavior now depends on formula edge cases, two databases staying in sync, an embedding model, and an external LLM, all currently verified only by ad-hoc manual spot checks recorded in `security-preventions.md`. Worth prioritizing targeted tests around formulas, request validation, ranking, reinforcement decisions, and dual-store failure behavior before this project's scope grows further — not urgent enough to stop and do now.

- **`SearchInput.limit`/`GenerateInput.limit` have a lower bound but no upper one** — `Field(default=5, ge=1)` on both (see the "No validation on `limit`" Resolved entry below for why the lower bound exists) but nothing stops a caller from requesting an arbitrarily large `limit`. Flagged by external review: `search_memories()`'s candidate pool is capped at `CANDIDATE_POOL_SIZE` (50) regardless, so a request for `limit=500` silently returns at most 50 — a caller has no way to know that from the API contract alone. For `/generate` specifically, a large `limit` also means more memories folded into the prompt and more reinforcement-guardrail comparisons per request. Reasonable bounds per the review: `1 <= limit <= 50` for search (matching `CANDIDATE_POOL_SIZE`), something tighter like `1 <= limit <= 10` for generate (default stays 5). Not yet implemented.

- **Stored prompt injection is a real risk if this ever needs write-integrity guarantees, not just abuse-volume limits.** Already documented (see `security-preventions.md`'s "Analytics panel..." entry and the general no-auth design decision), but an external review correctly pointed out the severity framing undersold one thing: retrieved memory text is concatenated directly into the system message sent to the model (`generate.py`), so any anonymous caller storing text via `/memories` can attempt to plant standing instructions the model sees on every future retrieval of that memory — not just a one-off disclosure risk, a persistence risk. Rate limiting (already in place) bounds *how fast* someone can do this, not *whether* it's possible at all, so it doesn't actually address this class of risk. Live-tested this session with 6 planted injection attempts (fake system-override text, a fake `</system>` tag, a fake payment-scam instruction) at deliberately high `impact` to maximize persistence — in every case tested, the model declined to comply and stayed in character, but that's the underlying model's own alignment doing the work, not a code-level defense in this repo. Masi Memory's no-auth design is a deliberate, settled product decision (meant to stay a fully open system) — so the fix menu here needs to stay inside that constraint rather than assume auth is coming: explicit data/instruction delimiting around the retrieved-memories block in the system prompt, and possibly basic sanity limits (length, content) on stored text, are the realistic options. Not investigated further yet.

- **Backend has no readiness handling for Postgres/Qdrant during container startup.** Compose's `depends_on` only guarantees dependency containers are *started*, not that they're actually ready to accept connections — `main.py`'s lifespan startup queries both immediately, with no health check or retry/backoff. Flagged by external review; plausible on a cold `docker compose up` where Postgres/Qdrant take a moment longer to accept connections than the backend takes to reach its first query. Needs either Compose-level health checks gating the backend's start, or a retry/backoff loop in the backend's own startup code. Not yet reproduced locally (this project's dev environment happens to start fast enough in practice), so severity is unconfirmed, but the missing safeguard itself is real.

- **`VECTOR_SIZE` is hardcoded while `EMBEDDING_MODEL` is environment-configurable.** `database.py` reads `EMBEDDING_MODEL` from the environment but `VECTOR_SIZE` (used to create the Qdrant collection) stays a fixed constant matching Qwen3-Embedding-0.6B's 1024-dim output. Flagged by external review: swapping to a model with a different output dimension via the env var alone, without also changing `VECTOR_SIZE` to match, would silently create a dimension-mismatched collection rather than fail loudly. No startup-time check confirms the two agree, and existing collections are never checked for compatibility either. Fix is either to remove the runtime model-swap capability (state plainly that changing `EMBEDDING_MODEL` requires a matching manual `VECTOR_SIZE` change) or derive/validate the dimension at startup instead of hardcoding it.

- **Code-quality items from an external review — five confirmed directly, the rest still unverified.** Confirmed by reading the actual code: `retrieval_count` (`database.py`) is written by `increment_retrieval_counts()` but never selected/read back anywhere in the backend or frontend — genuinely dead state, not just "possibly." `normalize_id()` is called once in `generate.py:127` on a candidate id before `reinforce_memory()` is invoked, and `reinforce_memory()` (`memory_operations.py:29`) calls `normalize_id()` again on entry — redundant, though harmless (idempotent). `formulas.compute_cosine_similarity()` does use `zip(vector_a, vector_b)` for the dot product, which silently truncates to the shorter vector's length on a mismatch rather than erroring, and `dot / (norm_a * norm_b)` has no guard against a zero-norm vector, which would raise an uncaught `ZeroDivisionError` — currently only reachable if the embedding model ever produced an all-zero vector, not observed in practice. `MemoryInput.text`/`SearchInput.text`/`GenerateInput.text` (`models.py`) are plain `str` with no `min_length` or blank/whitespace validator — an empty or whitespace-only memory or query is accepted and stored/embedded as-is.

  Also confirmed by reading the code: `store_memory()`'s only caller is `routers/memories.py`'s `POST /memories` route, which passes just `(body.text, body.impact)` — no current caller passes `created_at`/`last_reinforced_at`, so those parameters are exactly as described in the "Seeded memories all looked freshly created" Resolved entry below: a real, tested capability with no live caller today. `psycopg2.connect()` (`database.py`) passes no `connect_timeout` or statement-timeout option — confirmed missing. `/generate`'s reinforcement loop (`generate.py`) calls `reinforce_memory(pid)` directly inside a `for` loop with no `try`/`except` around it — if one call raises partway through (e.g. a transient DB error on the 3rd of 5 qualifying memories), the earlier ones stay reinforced (each is its own atomic `UPDATE`) while the request itself fails, confirming the partial-success/500 concern. `answer = response.choices[0].message.content` (`generate.py:82`) is accessed with no shape check — an OpenAI response with an empty `choices` list would raise an uncaught `IndexError`; `content` being `None` (e.g. certain refusal/filter responses) wouldn't crash but would silently return `{"answer": null, ...}` to the caller.

  Still not individually verified: Qdrant's payload text and Postgres's metadata drifting apart with no reconciliation process — a genuine design-level risk given the two-store split (see `techStack.md`), but not a specific code defect to point at the way the others above are.

- **Public repo exposes schema docs** — `dataModel.md` and `techStack.md` document internal DB structure. Acceptable for a dev/portfolio project with no real users. Revisit if this becomes a real product.

- **No `start.sh` script** — collection creation and any future startup logic runs inline on app start. If startup complexity grows (migrations, health checks, seed data), consolidate into a `start.sh` script.

- **Rate limiter doesn't surface `RateLimit-*` response headers** — verified live that neither successful nor blocked responses currently include the standard rate-limit informational headers (remaining requests, reset time) that `slowapi`/`SlowAPIMiddleware` support. Not a security or correctness issue — the actual enforcement works correctly regardless (verified separately, see `security-preventions.md`) — just means callers (including the frontend, if it ever wants to show "you're close to the limit") can't currently introspect their remaining allowance. Likely needs an explicit config flag on the `Limiter`/middleware setup; not investigated further yet.

- **Reinforcement guardrail's embedding signal has a measured precision ceiling for short text.** `REINFORCEMENT_GUARDRAIL_THRESHOLD` was lowered from `0.85` to `0.8` specifically because a genuine citation buried in a parenthetical clause scored *lower* (`0.81`-`0.83`) than a filler phrase from the original calibration set (`0.837`) — the two measurably overlap at fine granularity, so no threshold value fully separates them (see `security-preventions.md`'s Resolved section). An embedding-OR-literal-overlap check was proposed then to recover under-scored genuine citations but was not built; the later lexical check described below was built as an AND for the opposite problem, reducing false positives.

  **A version of the hybrid check has since been built** (`formulas.shares_significant_word()`), but as an AND, not the originally-proposed OR: a memory now needs BOTH the embedding threshold AND literal word overlap with its best-matching sentence, not either alone. Built for a different, newly-discovered failure mode than the one the OR-proposal targeted: not missed genuine citations (under-scoring), but confidently-wrong reinforcement of an unrelated memory that happens to share narrative *shape* with the real citation ("tried X, had a bad reaction, gave up on X" — found live reinforcing a kombucha memory and a spicy-wings memory against an answer sentence actually about giving up on gas-station sushi, `0.82`/`0.82` against threshold `0.8`, zero shared content). Verified against the existing calibration set before trusting it: the parenthetical Toontown citation still passes (shares "Toontown"), the original ~15-phrase filler set still fails (nothing to share), the new case now correctly fails. See `security-preventions.md`'s Resolved section for the full account.

  **Not fully closed, and accepted as such rather than chased further right now**: re-testing found a second, narrower collision the word-overlap check doesn't catch — words that are only generic *in this specific seeded dataset* (e.g. "tried"/"first," from many memories repeating a "Tried X for the first time" template) aren't in a hand-picked stopword list, so they can still satisfy the overlap requirement without the memory actually being the one discussed. A hand-picked stopword list is inherently reactive — it only catches genericness anticipated in advance, and every dataset's own repeated phrasing will expose different gaps the same way. The more robust version — a word counts as significant based on how rare it actually is across the stored memory corpus, not a fixed list — would close this generally instead of one collision at a time, but needs real corpus-frequency infrastructure (computed and kept current somehow) that doesn't exist yet. Accepted as a known-imperfect tradeoff, same category as `REINFORCEMENT_GUARDRAIL_THRESHOLD` itself: a real, measured improvement, not a claim of full precision. Revisit if this becomes a frequent, not just occasional, recurring problem — same bar the original threshold decision was held to.
- **Validate MVP retrieval weights (`0.95`/`0.00`/`0.05`) on a frozen, broader evaluation dataset.** The original re-ranking problem (retrievability displacing genuinely relevant memories, up to a 15+ point Recall@5 drop) was diagnosed and resolved — see `evaluation/experiments/reranking-weight-decision.md` for the full record and `security-preventions.md`'s Resolved section for the summary. What's left is validating that the *chosen replacement* holds up beyond the conditions it was picked under:
  - Current weights are provisional MVP defaults, chosen from one evaluation round, not validated as broadly correct.
  - The fixture is hand-built (23 positive cases, 4 negative controls) by one person reasoning about one seeded dataset — not independently sourced, not large.
  - Experiments used a frozen candidate set *within* each run (every ranking variant compares against identical data), but not a persistent snapshot *across* sessions — re-running this evaluation next month, after more organic reinforcement, could show a different picture even with unchanged code. See the `--snapshot` entry below.
  - Future evaluation should broaden this: more users' data (not just one person's memories), differently-reinforced database states, more ambiguous/adversarial queries, and a larger set of relevance judgments than 23 hand-labeled cases.
  - `frequency` at its current weight (`0.05`) wasn't measured as harmful on this fixture, but isn't fully vindicated either — the same heavily-reinforced memories that dominated under high `retrievability` still intrude into some unrelated queries' top-5 purely from `frequency`, even at `retrievability=0.00`. Worth more scrutiny before assuming `0.05` is safe at a larger scale, not just "didn't move the needle on 23 queries."
- **`evaluation/evaluate_retrieval.py` only supports live-database evaluation, which isn't trustworthy for comparing ranking-weight changes across separate sessions.** Every run reads whatever `stability`/`use_count`/`last_reinforced_at` currently exist in the live dev DB — values that keep shifting as the system gets used (every real reinforcement event moves them). The actual re-ranking-weight decision (see above) reached this exact tradeoff point and deliberately proceeded without building `--snapshot` mode anyway: every ranking variant *within* a single run/invocation shares one frozen, once-fetched candidate set (guaranteeing a fair comparison *between weight combinations tested together*), which was judged sufficient for that decision — the risk `--snapshot` would close is specifically *cross-session* comparison (this month's run vs. next month's), not the within-run comparisons the actual weight choice was based on. Proposed fix, still discussed but not built: a `--snapshot <file>` mode that captures the current per-candidate signals once and evaluates repeatedly against that frozen copy, so future re-validation (see the entry above) can compare against a fixed reference point rather than whatever the live database happens to look like whenever it's re-run. Revisit if/when re-validating the MVP weights on a broader dataset, or if any future weight change needs a genuine multi-session before/after comparison.
- **`MIN_RETRIEVABILITY = 0.01` is an MVP default, not a validated one.** Chosen by calculating expected deletion ages across representative stability/impact/reinforcement combinations, then sanity-checking those numbers against this project's own live seeded dataset (see `scripts/forgetting_threshold_analysis.py` and `architecture.md`'s Decay-Based Forgetting section for the full reasoning) — a lighter review than the retrieval-weights decision above, by design. Same caveats apply, arguably more so:
  - Chosen from one round of reasoning about one hand-built, single-person, decades-backdated seeded dataset — not independently sourced, not validated against real usage patterns.
  - No claim these lifetimes (~13.7-54.8 years, never reinforced) match real human forgetting curves — the number was picked because it stopped looking obviously wrong for this dataset, not because it was derived from anything biological.
  - `FORGETTING_DRY_RUN` (see `main.py`) defaults to `true` specifically because this is untested against a real forgetting cycle — flip it only after inspecting at least one full dry-run cycle's logged output.
  - Revisit once the system has real, organically-aged usage history rather than synthetically backdated seed data — the current numbers are a starting point for "not obviously wrong," not a tuned target.
- **Neuroscience/psychology terminology could be reframed more precisely, per an external review with sourced citations.** The docs are already deliberately hedged throughout (see `security-preventions.md`/`architecture.md`'s repeated "loosely inspired, not a claim that..." framing), and the review confirmed several of those existing caveats as accurate (permanent deletion vs. biological forgetting being about inaccessibility rather than erasure; Qwen3-Embedding's instruction-awareness). Specific reframing suggestions not yet acted on: describe the system as "a RAG memory store with cognitively inspired decay and use-based persistence heuristics" rather than "a simplified implementation of human memory," since `stability`/`retrievability` are spaced-repetition-inspired engineering variables, not modeled neuroscientific state variables; the flashbulb-memory analogy (`impact` seeding durability) should emphasize vividness/confidence rather than superior accuracy or durability, since flashbulb memories are known to still distort and fade; the fixed `1.2×` reinforcement multiplier is a much simpler story than biological reconsolidation, which can strengthen, weaken, or update a memory depending on conditions this system doesn't model; and "meaningful use" (the reinforcement guardrail) detects textual reflection in an answer, which is materially different from proving a memory causally influenced generation. Also worth stating plainly: the `frequency` signal's exposure/reinforcement separation reduces the self-reinforcing popularity feedback loop (popular memories get shown more, cited more, ranked higher) but doesn't fully eliminate it, since reinforcement still depends on retrieval happening at all. None of this changes any actual behavior — it's a documentation-precision backlog, not a code fix.

- **Non-atomic dual-store writes/deletes** — `store()` (Qdrant then Postgres) and `delete_memories()` (Postgres then Qdrant) are each two sequential operations, not one atomic one. If the first succeeds and the second fails mid-request (network blip, one store briefly down), the result is a permanently orphaned record in whichever store didn't get the matching write. `search_memories()` already tolerates a Qdrant-only orphan by skipping it (no Postgres row to rank against), but nothing ever cleans it up — Decay-Based Forgetting's `get_all_memories()` only reads Postgres, so a Qdrant-only orphan is invisible to it forever, and a Postgres-deleted-but-Qdrant-still-has-it orphan is equally invisible. Real fix needs either a reconciliation job cross-checking both stores, or a retry/compensating-action pattern around the two writes. Low probability (requires one store to fail mid-request specifically), not worth the added complexity yet.

## Considered & Rejected

- **Difficulty parameter** (per-memory, affects how much reinforcement boosts stability) — rejected for now. FSRS-style Difficulty is only useful because it's learned from real outcome data (pass/fail review ratings); this system has no equivalent feedback signal, so it'd just be a stored number nothing meaningfully drives. Revisit if a real "was this memory actually useful" feedback loop gets built.
- **Confidence parameter** (how trustworthy the memory's content is, distinct from impact/importance) — genuinely useful idea, not redundant with `impact`, but deferred — not needed for v1's ranking to work. Would need its own term in the ranking formula, not routed through `stability` like impact is.
- **Separate importance / attention_quality / understanding / emotional_salience fields** — rejected. All collapse into the single `impact` field ("how significant/emotionally weighted is this to me"); no clear signal distinguishes them from each other or from impact, and several (attention_quality, understanding) have no natural input signal at all for a system storing text via an API call.
- **Variable reinforcement_gain** (`1.1 + 0.2 × (1 - retrievability)` — bigger stability boost for memories that had decayed further before being reinforced) — good future improvement, models the real spacing effect more accurately than a fixed multiplier. Deferred: the fixed `REINFORCEMENT_MULTIPLIER = 1.2` is simpler and good enough to start collecting real usage data before tuning something more elaborate.
- **Migrations** — not using, personal project.
- **ORM (SQLAlchemy)** — considered for Postgres interaction. Rejected — one table, simple queries (insert, update stability, delete where computed retrievability < threshold). Raw SQL with psycopg2 is cleaner and easier to reason about for this project size. Revisit if schema complexity grows significantly.

## Resolved

- **Reverse proxy trust — built and tested, then made unnecessary by a later architecture decision, not by any code change.** `backend/rate_limit.py`'s `get_rate_limit_key()` previously called `slowapi`'s `get_remote_address()`, which only ever reads `request.client.host` — correct with nothing in front of Uvicorn, but would have broken (every real visitor collapsing into one shared rate-limit bucket) once Traefik went in front, per the original `prod.md` plan. Fixed at the application layer at the time: `backend/trusted_proxy.py` (`resolve_client_ip()`) walks `X-Forwarded-For` right-to-left, trusting a hop only if it's in `TRUSTED_PROXY_IPS` (empty by default — trusts nobody), stopping at the first untrusted hop so an attacker-prepended fake IP is never reached. Covered by `backend/test_trusted_proxy.py` (13+ cases: multi-hop chains, spoofing attempts, malformed input, IPv4/IPv6, CIDR ranges, invalid config) and verified live against the dev server (a genuine 20-request burst limit + `429` on the 21st, a separate bucket for a second forwarded IP, admin bypass still working).

  **Superseded, not obsolete**: `prod.md` later dropped Traefik/any reverse proxy from the deployment plan entirely (see its "TLS & Reverse Proxy" section) — Uvicorn terminates TLS directly, so `request.client.host` is always the real caller with nothing to interpret, and `TRUSTED_PROXY_IPS` needs no real-world value for this deployment. The code and its test coverage aren't wasted: they stay in the codebase as a genuinely tested, dormant capability, useful again if a reverse proxy (e.g. Cloudflare, for DDoS protection — see `prod.md`'s "Generation API" section) is ever added later, at which point `TRUSTED_PROXY_IPS` gets a real value and the test matrix gets re-run through it, same as originally planned.

- **Double startup on uvicorn reload** — collection creation was running at module level, firing twice due to uvicorn's reloader process. Fixed by moving startup logic into FastAPI's lifespan context manager, which only runs in the server process.
- **No services layer** — resolved differently than originally proposed. Rather than extracting business logic into a separate services module, the decision was: routers own business logic (validation, clamping, computing derived values) directly, and `database.py` stays a plain data-access layer with no logic of its own. See the "Code Architecture (MVC)" section in `architecture.md`.
- **POST endpoint uses query param** — already resolved before this item was written; `store()` has always taken a Pydantic request body (`MemoryInput`), never a query param. Stale tech-debt entry, removed.
- **Forgetting could die permanently on one bad row** — `delete_decayed_memories()`'s per-memory loop had no error handling; a row with `stability <= 0` (nothing in the schema prevents this — only app-level clamping at write time) would raise an uncaught exception that killed the entire background `asyncio` loop in `main.py`, silently disabling forgetting for the rest of the process's life with no log or alert. Fixed: the per-row computation is now wrapped in `try/except ValueError`, logging and skipping the bad row instead of crashing the loop. (Originally caught `ZeroDivisionError` too, from `impact` dividing the deletion threshold — no longer possible once the threshold became flat/impact-independent, see the `MIN_RETRIEVABILITY` entry above.)
- **`/generate` could 500 on a malformed tool call** — a `reinforce_memory` tool call missing the `id` argument raised an uncaught `KeyError` (not a `ValueError`, so the existing except clause didn't catch it), crashing the whole request. Fixed: broadened the catch to `(ValueError, KeyError)`.
- **No validation on `limit`** — `SearchInput.limit`/`GenerateInput.limit` had no lower bound; a negative value (e.g. `-1`) made `ranked[:limit]` silently return all-but-the-last result instead of erroring. Fixed: `Field(default=5, ge=1)` on both.
- **`reinforced_memory_ids` echoed a non-canonical id** — `/generate`'s response appended the model's raw tool-call argument string rather than the normalized UUID actually written to Postgres; a differently-cased but validly-formatted id could look mismatched to a caller comparing against Postgres's canonical form. Fixed: `reinforce_memory()` now returns the normalized id, and `/generate` uses that instead of the raw argument.
- **Seeded memories all looked freshly created** — `seed.py` creates everything via `POST /memories`, which always defaults `created_at`/`last_reinforced_at` to `NOW()`, so every seeded memory ended up equally "just created" with no age variation to exercise decay/forgetting/the `[time ago]` prompt marker against. `store_memory()`/`insert_memory()` gained optional backdating parameters to solve this generally, but resolved differently for `seed.py`'s actual need: `scripts/backdate.sh`, a small dev-only script, runs a single SQL `UPDATE` directly against Postgres after seeding — no Python dependency changes, no switch to calling `store_memory()` in-process needed. Went through two designs since: initially spread every memory uniformly across the last 3 years, then backdated based on each memory's `memory_type` category to a random offset within a life-stage range (`childhood`/`teen`/`young_adult`) — see the next entry for why that second design was itself replaced. The optional parameters remain in `store_memory()`/`insert_memory()` regardless, as a real, working, tested capability for any future in-process caller — see `security-preventions.md`'s Confirmed Clean entry. See `scripts.md` for the current design.

- **`backdate.sh` had no awareness of narrative dependencies between memories, and this caused real bugs** — the `memory_type`-category/random-range design assigned each row a fully independent random timestamp within its category's range, with no concept that some memories are causally ordered (e.g. an "acquired a pet" memory must precede that pet's "passed away" memory). This produced 3 real contradictions in the seeded dataset: a memory about a pet's death landed before both memories about her being acquired, and two memories referencing "after \[a pet\] passed" landed years before that pet's own death memory. All three were found by manual inspection and fixed with one-off `UPDATE`s at the time, not by any tooling. Fixed properly, not just patched, by a larger redesign: `impact` and `created_at` are no longer randomly generated at all — `scripts/seed_data.json` now hand-assigns both per memory, with dates chosen against a real, internally consistent timeline, so a dependency like "acquired before died" is encoded once, correctly, by whoever writes the dataset, rather than left to chance on every reseed. `memory_type` itself was removed entirely in the same pass (see the entry below) — it had no remaining purpose once category-based random backdating was gone, and it was never read anywhere else in the system (not ranking, not decay, not the `/generate` prompt). See `scripts.md` for the current `seed.py`/`seed_data.json`/`backdate.sh` design.

- **`memory_type` removed entirely — schema, API, and both seed scripts** — added originally so `backdate.sh` could apply a life-stage-appropriate random age range per memory (see the two entries above). Once `backdate.sh` moved to hand-assigned, per-memory dates instead of category-random ranges, `memory_type` had no remaining consumer anywhere: confirmed by grepping the whole codebase before removing it — it was never read by ranking, decay, `/generate`'s prompt, or the frontend, only ever written and stored. Removed from `CREATE_MEMORIES_TABLE`, `insert_memory()`, `MemoryInput`, and `store_memory()`/`store()`. No migration needed — this project doesn't use migrations by design (see "Considered & Rejected" below); `scripts/clear.sh` gives every dev environment a fresh schema instead. A live-tested "MemoryInput.memory_type has no app-level length validation" security gap (`security-preventions.md`'s old "To Add" section) is now moot rather than fixed, since the field it described no longer exists.
